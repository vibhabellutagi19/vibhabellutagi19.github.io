20:T4040,<p>Commit a project with three files. Change one line in one of them and commit again.</p>
<p>You might expect Git to have stored the project twice. It didn&#39;t. The second commit added three small objects: the new version of the file that changed, a new list of the root folder, and the commit itself. Everything else, including a whole subfolder, is shared between both commits.</p>
<blockquote>
<p>Git names everything by the hash of its content, so identical content is only ever stored once.</p>
</blockquote>
<p>In the <a href="/blog/git-essentials">previous post</a> we used Git through its commands. This post opens the <code>.git</code> folder: the four object types Git stores, what happens inside it during two real commits, and what the rest of the folder is for.</p>
<h2 id="four-object-types-store-everything">Four Object Types Store Everything<a class="heading-anchor" href="#four-object-types-store-everything" aria-label="Link to this section">#</a></h2>
<p>Git is a <code>content-addressable file system</code>. All data is stored as objects, and each object is identified by the <strong>SHA-1 hash</strong> of its content. Git doesn&#39;t track individual file edits; it stores snapshots of your project&#39;s directory structure, built from four object types:</p>
<ul>
<li><strong>Blobs (Binary Large Objects):</strong> These store the <code>actual content of a file</code>. A blob doesn&#39;t store metadata like the file name or permissions; it&#39;s purely the data. If two files have identical content, even in different locations or commits, they <strong>share the same blob object</strong>.</li>
<li><strong>Trees:</strong> These represent <code>directories</code>. A tree stores file modes (permissions), object types (blob or another tree), SHA-1 references and <strong>file names</strong>. A root tree points to blobs (files) and other trees (subdirectories).</li>
<li><strong>Commits:</strong> These represent a <code>specific version or snapshot</code> of the project. A commit points to a root tree and stores the author, committer, date and message. Crucially, it also references its <strong>parent commits</strong>, which makes the history a directed acyclic graph (DAG).</li>
<li><strong>Tags:</strong> These give a permanent name to a specific commit, often used for version releases.</li>
</ul>
<p><img src="/posts/2026-01-16-inside-git/assets/git-object-model.png" alt="git-object-model" loading="lazy" /></p>
<h2 id="watching-git-store-two-commits">Watching Git Store Two Commits<a class="heading-anchor" href="#watching-git-store-two-commits" aria-label="Link to this section">#</a></h2>
<p>Let&#39;s see these objects for real. We&#39;ll create a repository, make two commits, and &quot;X-ray&quot; the <code>.git</code> folder after each one.</p>

<p>Git created a new blob for the modified story.txt and a new root tree to list it. Now look at the <code>stories</code> directory. We didn&#39;t touch it, so its content didn&#39;t change, so its hash didn&#39;t change. Git doesn&#39;t make a copy; the new root tree simply points to the existing <code>stories</code> tree from the first commit.</p>
<p>That&#39;s the opening of this post in practice: one changed file cost one new blob, one new tree and one commit object. This is also where the &quot;graph&quot; in DAG comes from: commits point to their parents, and trees from different commits point to the same objects.</p>

<h2 id="the-git-folder-is-the-repository">The .git Folder Is the Repository<a class="heading-anchor" href="#the-git-folder-is-the-repository" aria-label="Link to this section">#</a></h2>
<p>Your project files are just one checked-out version. The repository itself, every version of every file, lives in <code>.git</code>:</p>
<ul>
<li><strong>HEAD:</strong> points to the current branch reference, i.e. which branch is checked out.</li>
<li><strong>config:</strong> repository-specific configuration settings.</li>
<li><strong>refs:</strong> references to branches and tags. A branch is just a file containing a commit hash.</li>
<li><strong>objects:</strong> every blob, tree, commit and tag, compressed.</li>
<li><strong>index:</strong> the staging area, the draft of your next tree.</li>
</ul>
<p><img src="/posts/2026-01-16-inside-git/assets/git-folder.png" alt="git-folder" loading="lazy" /></p>
<hr>
<p>Git looks like a set of commands, but underneath it&#39;s a small database where every object is named by its content. That&#39;s why it&#39;s fast (most work is local), why its history can&#39;t be silently altered (change a byte and the hash changes), and why committing a one-line change to a large project costs almost nothing.</p>
