13:T1fd7,<p>In the previous post, we learnt <a href="/blog/git-essentials/">How Git manages version control</a> through its internal structures. In this continuation, we will delve deeper into how git works internally and the specific components of the <code>.git</code> folder and their functions.</p>
<h2>Git Object Model</h2>
<p>Git tracks changes by operating as a <code>content-addressable file system</code>, meaning all data is stored as objects and identified by a unique <strong>SHA1 hash</strong> based on their content, rather than tracking individual file edits, Git manages snapshots of your project&#39;s directory structure through a hierarchy of specific object types.</p>
<ul>
<li><strong>Blobs (Binary Large Objects):</strong> These store the <code>actual content of a file</code>. A blob does not store metadata like file names or permissions; it is purely the data itself. If two files have identical content, even in different locations or commits, they will <strong>share the same blob object</strong>.</li>
<li><strong>Trees:</strong> These represent <code>directories</code>. A tree object stores file modes (permissions), object types (blob or another tree), SHA1 references, and <strong>file names</strong>. This allows Git to build a hierarchical structure where a root tree points to blobs (files) and other trees (subdirectories).</li>
<li><strong>Commits:</strong> These represent a <code>specific version or snapshot</code> of the project. A commit object points to a root tree and includes metadata such as the author, committer, date, and a commit message. Crucially, it also references <strong>parent commits</strong>, creating a directed acyclic graph (DAG) that forms the project&#39;s history.</li>
<li><strong>Tags:</strong> These provide a permanent reference to a specific commit, often used for version releases.</li>
</ul>
<p><img src="/posts/2026-01-16-inside-git/assets/git-object-model.png" alt="git-object-model" loading="lazy" /></p>
<h2>How Git Tracks Changes</h2>
<p>Let&#39;s look at the internals practically. We will create a repository, make two commits, and then &quot;X-ray&quot; the .git folder to see how Git maps these objects together.</p>
<p>The Setup<br>We start with a simple project structure:</p>
<pre><code class="language-project/">├── story.txt
└── stories/
    └── story.txt
    └── readme.md
</code></pre>
<p>We initialize the repository (git init), which creates the hidden .git directory—the database where all our objects will live.</p>
<pre><code class="language-bash">❯ git init

&gt; Initialized empty Git repository in /path/to/project/.git/
</code></pre>
<p>The Staging Area (The Index)<br>Before we commit, we must add files.</p>
<pre><code class="language-bash">❯ git add . -- adds all files to the staging area
</code></pre>
<p>What just happened internally? Git isn&#39;t just listing filenames. It is taking the content of every file, compressing it into a Blob (Binary Large Object), hashing it, and storing it in the .git/objects folder. The Index (or Staging Area) is a draft manifest. It maps your filenames to these new Blob hashes. It acts as a &quot;construction zone&quot; where the next tree is currently being assembled.</p>
<p>Commit 1: The Initial Snapshot</p>
<p>We commit our work:</p>
<pre><code class="language-bash">
❯ git commit -m &quot;first commit&quot;
&gt; [main (root-commit) 90ae710] first commit
&gt; 3 files changed, 3 insertions(+)
&gt;  create mode 100644 stories/metadata.txt
&gt;  create mode 100644 stories/readme.md
&gt;  create mode 100644 story.txt
</code></pre>
<p>Now, let&#39;s play detective. We have a commit hash (90ae710). We can use <code>git cat-file -p (pretty print)</code> to look inside this object.</p>
<pre><code class="language-bash">❯ git cat-file -p 90ae710

tree 78f57e9cce76cd70270e8e678fe13166c6aa3874
author  &lt;author&gt; 1768598520 +0100
committer &lt;author&gt; 1768598520 +0100

first commit
</code></pre>
<p>The commit object is tiny. It contains meta-data (author, time) and a single pointer to a Root Tree (78f57e9).</p>
<p>Let&#39;s look inside that Root Tree:</p>
<pre><code class="language-bash">
❯ git cat-file 78f57e9 -p
040000 tree a096f175360d158908baf1f8c25378635e90e9ea	stories
100644 blob f6d043db0fd669f2d8685b634b662e39fdacaf12	story.txt
</code></pre>
<p>This tree represents our project root. It points to one blob (story.txt) and another tree (stories folder). If we follow the stories tree (a096f1), we find the blobs for metadata.txt and readme.md.</p>
<p>Visualizing Commit 1 Here is how Git has mapped these objects. Note that arrows point away from the commit snapshot to the data.</p>
<p>Again when we look inside the <code>stories</code> tree object, we can see the files inside that directory:</p>
<pre><code class="language-bash">
❯ git cat-file a096f1 -p
100644 blob f6d043db0fd669f2d8685b634b662e39fdacaf12	metadata.txt
100644 blob 8728a858d9d21a8c78488c8b4e70e531b659141f	readme.md
</code></pre>
<p>Commit 2: The Evolution (The DAG)<br>Now, let&#39;s modify story.txt and commit again.</p>
<pre><code class="language-bash">❯ echo &quot;Additional content&quot; &gt;&gt; story.txt
❯ git add .
❯ git commit -m &quot;second commit&quot;
[main d61c92a] second commit
 1 file changed, 1 insertion(+)
</code></pre>
<p>If we check the logs, we see a linear history:</p>
<pre><code class="language-bash">❯ git log --oneline

d61c92a (HEAD -&gt; main) second commit
90ae710 first commit
</code></pre>
<p>But the internal structure is more interesting. Let&#39;s inspect the Second Commit (d61c92a):</p>
<pre><code class="language-bash">git cat-file d61c92a -p
tree 20ce426f8e3fdd9f1fd72813fa6674113df20781
parent 90ae71002a1512aa87565bead79f205a3469f58d

second commit
</code></pre>
<p>The Efficiency of Git Git created a new Blob for the modified story.txt and a new Root Tree to list it. However, look at the stories directory. We didn&#39;t touch it. Because the content inside stories/ didn&#39;t change, the hashes didn&#39;t change. Git doesn&#39;t create a copy; it simply points to the existing tree object from the first commit. Visualizing the DAG This is where the &quot;Graph&quot; in DAG comes from. Git reuses unchanged objects to save space and ensure integrity.</p>
<p><img src="/posts/2026-01-16-inside-git/assets/git-dag.svg" alt="git-dag|w=550" loading="lazy" /></p>
<h2>The .git Folder - The Real Repository</h2>
<p>The <code>.git</code> folder is the heart of a Git repository. It contains all the information about the repository, including configuration settings, references to branches and tags, and the object database that stores all the commits, trees, and blobs. Here are some key components of the <code>.git</code> folder:</p>
<ul>
<li><strong>HEAD:</strong> This file points to the current branch reference, indicating which branch is currently checked out.</li>
<li><strong>config:</strong> This file contains repository-specific configuration settings.</li>
<li><strong>refs:</strong> This directory contains references to branches and tags.</li>
<li><strong>objects:</strong> This directory stores all the Git objects (blobs, trees, commits, and tags) in a compressed format.</li>
<li><strong>index:</strong> This file represents the staging area, tracking the state of the working directory.</li>
</ul>
<p><img src="/posts/2026-01-16-inside-git/assets/git-folder.png" alt="git-folder" loading="lazy" /></p>
<h2>Conclusion</h2>
<p>Understanding the internal workings of Git—the object model, the DAG, and the structure of the <code>.git</code> folder demystifies the tool we use daily. It explains why Git is so fast (local operations, efficient compression), why it&#39;s robust (immutable history, content integrity), and how it manages complex branching and merging.</p>
<p>By seeing Git not just as a set of commands but as a sophisticated content-addressable file system, we can better troubleshoot issues, optimize our workflows, and appreciate the elegance of its design. In the next post, we will explore advanced Git concepts like rebasing and cherry-picking, building on this foundational knowledge.</p>
