In that moment, a server you&#39;ve probably never heard of may have asked three other servers where google.com lives, and none of them, on its own, knew the full answer.</p>
<blockquote>
<p>DNS works because no server knows everything. Each one only knows who to ask next.</p>
</blockquote>
<p>This post follows a single lookup through that chain: what DNS is, the three layers of servers it asks, why it&#39;s split up that way, and how to watch each step yourself with <code>dig</code>.</p>
<h2 id="dns-is-the-internets-phonebook">DNS Is the Internet&#39;s Phonebook<a class="heading-anchor" href="#dns-is-the-internets-phonebook" aria-label="Link to this section">#</a></h2>
<p>Every device on the internet is reached by an <a href="https://en.wikipedia.org/wiki/IP_address">IP address</a>, a numerical label like <em>192.0.2.1</em>. Remembering the IP address of every website you visit would be like remembering the phone number of everyone you know, without a contacts app.</p>
<p>The Domain Name System (DNS) is that contacts app. It&#39;s a hierarchical, distributed <a href="https://en.wikipedia.org/wiki/Name_service">name service</a> that turns human-readable names like <code>google.com</code> into the IP addresses machines use to talk to each other. That conversion is called <strong>name resolution</strong>.</p>
<h2 id="dig-lets-you-ask-dns-yourself">dig Lets You Ask DNS Yourself<a class="heading-anchor" href="#dig-lets-you-ask-dns-yourself" aria-label="Link to this section">#</a></h2>
<p><code>dig</code> (Domain Information Groper) is a command-line tool that sends DNS queries and shows you the full answer. When you type <code>google.com</code> into your browser, DNS works quietly in the background; <code>dig</code> lets you ask the same question yourself and see the details. It&#39;s the tool DNS administrators reach for first when troubleshooting.</p>
<p>When you run <code>dig google.com</code>, you get a report with sections like:</p>
<p><strong>1. Question Section</strong> - What you asked</p>
<div class="code-block">
      <div class="code-head">

      </div>
      <pre class="shiki"><code>;; QUESTION SECTION:
;google.com.                    IN      A</code></pre>
    </div><p>Translation: &quot;What is the A record (IP address) for google.com?&quot;</p>
<p><strong>2. Answer Section</strong> - The actual answer</p>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang"></span>

google.com.             300     IN      A       142.250.185.46</code></pre>
    </div><p>The <code>300</code> is the TTL: how many seconds this answer can be cached before someone has to ask again.</p>
<h2 id="three-layers-each-knowing-only-the-next">Three Layers, Each Knowing Only the Next<a class="heading-anchor" href="#three-layers-each-knowing-only-the-next" aria-label="Link to this section">#</a></h2>
<p>A lookup walks down a hierarchy: <strong>Root → TLD → Authoritative</strong>. Each layer knows a little, and points you to the layer below.</p>
<p><strong>Root Servers</strong> →<br>The root of the DNS tree, written as a dot (<code>.</code>). Every lookup that isn&#39;t cached starts here. Root servers don&#39;t know any domain&#39;s IP address; they only know which servers handle each top-level domain. There are 13 root server identities (<code>a</code> to <code>m.root-servers.net</code>), served by more than a thousand physical servers around the world.</p>
<p><strong>Top-Level Domains (TLD)</strong> →<br>If a website address is like a street address, the TLD is the country at the end. In <strong><a href="http://www.google.com">www.google.com</a></strong>, the TLD is <strong>.com</strong>. TLDs split the internet into manageable groups:</p>
<ul>
<li><strong>.com</strong> usually means a <strong>com</strong>mercial business (like Amazon or Google).</li>
<li><strong>.in</strong> is for India.</li>
<li><strong>.edu</strong> means an <strong>edu</strong>cational institution (like a university).</li>
<li><strong>.gov</strong> means a <strong>gov</strong>ernment agency.</li>
</ul>
<p>TLD servers don&#39;t know google.com&#39;s IP address either. They know which servers are <strong>authoritative</strong> for google.com.</p>
<p><strong>Authoritative Servers</strong> →<br>These are <strong>the official source of truth</strong> for a specific domain. They hold its actual DNS records (A, AAAA, MX, etc.) and give the final answer.</p>

<p>To watch the whole walk in one command, run <code>dig +trace google.com</code>. It starts at the root and follows each referral down, printing every step.</p>
<h3 id="why-split-it-up-scale-and-survival">Why Split It Up: Scale and Survival<a class="heading-anchor" href="#why-split-it-up-scale-and-survival" aria-label="Link to this section">#</a></h3>
<p><strong>Scalability</strong> - Could one person memorise every address in the world? No. But divide the world into countries, then cities, then streets, and each level only needs to know its own piece. The internet has hundreds of millions of domain names; no single server could answer for all of them. Splitting the work up gives each layer a manageable portion.</p>
<p><strong>Decentralisation</strong> - If there were one master directory and it went down or got hacked, the whole internet would break. Instead, DNS spreads the responsibility:</p>
<ul>
<li>13 root server identities, run by different organisations on more than a thousand servers</li>
<li>Different organisations manage different TLDs (.com, .org, .uk, etc.)</li>
<li>Individual companies manage their own authoritative servers</li>
</ul>
<p>If one piece fails, the rest keep working.</p>
<h2 id="the-resolver-does-the-asking-for-you">The Resolver Does the Asking for You<a class="heading-anchor" href="#the-resolver-does-the-asking-for-you" aria-label="Link to this section">#</a></h2>
<p>Your browser doesn&#39;t walk this chain itself. It hands the question to a <strong>recursive resolver</strong> (usually run by your ISP, or a public one like <code>1.1.1.1</code> or <code>8.8.8.8</code>), which does the walking and hands back just the answer:</p>
<ol>
<li><code>Request initiated</code> → You type a URL (e.g., <code>www.example.com</code>), and your device asks the recursive resolver for its IP address.<ol>
<li><strong>Cache Check</strong>: If this name was looked up recently, the resolver answers from its cache straight away.</li>
</ol>
</li>
<li><code>Query to the Root Server</code> → If it&#39;s not cached, the resolver starts at a root server, which replies with the TLD servers for <code>.com</code>.</li>
<li><code>Querying the TLD Server</code> → The <code>.com</code> TLD server replies with the authoritative servers for <code>example.com</code>.</li>
<li><code>Querying the authoritative DNS server</code> → The authoritative server replies with the actual IP address.</li>
<li><code>Returning the result to your device</code> → The resolver returns the IP to your device, and caches it for the record&#39;s TTL so the next lookup skips steps 2–4.</li>
</ol>
<p><img src="/posts/2026-01-23-how-dns-resolution-works/assets/image-1.png" loading="lazy" /></p>
<p>That cache is why most lookups are fast: the full walk only happens the first time someone using that resolver asks for a name.</p>
<hr>
<p>So when <code>google.com</code> loads instantly, it&#39;s not because one server knew the answer. It&#39;s because the root knew who handles <code>.com</code>, <code>.com</code> knew who handles google.com, and google.com&#39;s own servers finally knew the address.</p>
