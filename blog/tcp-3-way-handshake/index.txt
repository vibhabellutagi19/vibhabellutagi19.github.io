21:T26d1,<p>Before your browser sends a single byte of an HTTP request, it has already exchanged three packets with the server. None of them carry any data.</p>
<p>They exist so that both sides agree on one thing: which number each of them will start counting bytes from.</p>
<blockquote>
<p>The handshake isn&#39;t a greeting. It&#39;s how both sides synchronize sequence numbers, and every TCP guarantee is built on those numbers.</p>
</blockquote>
<p>This post covers why TCP is needed at all, what can go wrong on a network, the handshake step by step, how data is acknowledged, and how a connection is closed.</p>
<h2 id="ip-makes-no-promises-tcp-does">IP Makes No Promises; TCP Does<a class="heading-anchor" href="#ip-makes-no-promises-tcp-does" aria-label="Link to this section">#</a></h2>
<p><strong>TCP (Transmission Control Protocol)</strong> is one of the core protocols of the Internet Protocol Suite. It runs at the Transport Layer (Layer 4) and gives applications reliable, ordered, error-checked delivery of data.</p>
<p>It&#39;s needed because the layer below it, the Internet Protocol (IP), is <strong>unreliable</strong>: packets can be lost, duplicated, delayed or arrive out of order. Applications don&#39;t want to deal with that. A developer wants to write data into a stream and trust it arrives intact.</p>
<p>Think of TCP as a postal service with tracking and confirmation. When you send a package, you want to know:</p>
<ul>
<li>Did it arrive?</li>
<li>Did it arrive intact?</li>
<li>Did it arrive in the right order (if you sent several)?</li>
</ul>
<p>TCP answers all three for every byte. Web browsers, email clients, file transfers and SSH all rely on it.</p>
<hr>
<h2 id="six-ways-a-network-breaks-your-data">Six Ways a Network Breaks Your Data<a class="heading-anchor" href="#six-ways-a-network-breaks-your-data" aria-label="Link to this section">#</a></h2>
<table>
<thead>
<tr>
<th><strong>Problem</strong></th>
<th><strong>Description</strong></th>
<th><strong>TCP&#39;s Solution</strong></th>
</tr>
</thead>
<tbody><tr>
<td><strong>Packet Loss</strong></td>
<td>Networks are unreliable. Packets can be dropped due to network congestion, router failures, or buffer overflows.</td>
<td>Acknowledgments (ACKs) and retransmissions. The sender retransmits data if it doesn&#39;t receive an acknowledgment within a timeout period.</td>
</tr>
<tr>
<td><strong>Out-of-Order Delivery</strong></td>
<td>Packets can take different routes through the network and arrive in a different order than they were sent.</td>
<td>Sequence numbers. Each byte of data is numbered, allowing the receiver to reorder packets correctly.</td>
</tr>
<tr>
<td><strong>Data Corruption</strong></td>
<td>Bits can be flipped during transmission due to electrical interference or hardware issues.</td>
<td>Checksums. TCP includes a checksum in every segment to detect corrupted data.</td>
</tr>
<tr>
<td><strong>Duplicate Packets</strong></td>
<td>Network devices might accidentally send the same packet multiple times.</td>
<td>Sequence numbers help identify and discard duplicate packets.</td>
</tr>
<tr>
<td><strong>Flow Control</strong></td>
<td>A fast sender can overwhelm a slow receiver.</td>
<td>Sliding window mechanism that allows the receiver to tell the sender how much data it can handle.</td>
</tr>
<tr>
<td><strong>Congestion Control</strong></td>
<td>Too many senders can overwhelm the network itself.</td>
<td>Congestion control algorithms (like Slow Start, Congestion Avoidance) that detect network congestion and reduce sending rates.</td>
</tr>
</tbody></table>
<p>Notice how many of these rely on <strong>sequence numbers</strong>. That&#39;s why the connection can&#39;t start until both sides have agreed on them.</p>
<h2 id="the-handshake-is-about-sequence-numbers">The Handshake Is About Sequence Numbers<a class="heading-anchor" href="#the-handshake-is-about-sequence-numbers" aria-label="Link to this section">#</a></h2>
<p>Imagine starting a phone call with a friend:</p>
<p><strong>You:</strong> &quot;Hey, can you hear me?&quot; (This is the <strong>SYN</strong>: you&#39;re initiating contact)<br><strong>Friend:</strong> &quot;Yes, I can hear you! Can you hear me?&quot; (This is the <strong>SYN-ACK</strong>: they acknowledge you AND check that you can hear them)<br><strong>You:</strong> &quot;Yep, I hear you too!&quot; (This is the <strong>ACK</strong>: you confirm you got their response)</p>
<p>Now you both know the line works in both directions, and the actual conversation can start.</p>
<p>In TCP terms:</p>
<p><strong>Step 1: SYN (Synchronize)</strong></p>
<ul>
<li>The client sends a segment with the <strong>SYN flag</strong> set</li>
<li>It includes its <strong>initial sequence number (ISN)</strong>, say <code>seq=1000</code></li>
<li>Meaning: &quot;I want to connect, and I&#39;ll start numbering my bytes from 1000&quot;</li>
</ul>
<p><strong>Step 2: SYN-ACK (Synchronize-Acknowledge)</strong></p>
<ul>
<li>The server responds with <strong>both SYN and ACK flags</strong> set</li>
<li>It sends its own initial sequence number, say <code>seq=5000</code></li>
<li>It acknowledges the client&#39;s number: <code>ack=1001</code> (client&#39;s seq + 1)</li>
<li>Meaning: &quot;Got it. I&#39;ll start numbering from 5000, and I expect your next byte to be 1001&quot;</li>
</ul>
<p><strong>Step 3: ACK (Acknowledge)</strong></p>
<ul>
<li>The client sends an ACK back</li>
<li><code>seq=1001</code> (as the server expects)</li>
<li><code>ack=5001</code> (server&#39;s seq + 1)</li>
<li>Meaning: &quot;Got your number too. I expect your next byte to be 5001&quot;</li>
</ul>
<p><strong>Connection is now ESTABLISHED!</strong> Both sides know where the other starts counting.</p>
<aside class="callout callout-note">
      <p class="callout-title">Note</p>
      <div class="callout-body"><p>Real initial sequence numbers are random, not 1000 and 5000. That makes it much harder for an attacker to guess them and inject fake packets into a connection.</p>
</div>
    </aside>

<h3 id="every-byte-gets-a-number">Every Byte Gets a Number<a class="heading-anchor" href="#every-byte-gets-a-number" aria-label="Link to this section">#</a></h3>
<p>Once connected, TCP splits data into <strong>segments</strong>, each labelled with the sequence number of its first byte. The receiver acknowledges by saying which byte it expects next.</p>
<p><strong>Example:</strong> You send &quot;Hello World&quot; (11 bytes), numbering from 1 for readability:</p>
<ul>
<li>TCP sends two segments: <code>[SEQ=1, &quot;Hello&quot;]</code> and <code>[SEQ=6, &quot; World&quot;]</code></li>
<li>The receiver gets segment 1 → sends <code>ACK=6</code> (expecting byte 6 next)</li>
<li>The receiver gets segment 2 → sends <code>ACK=12</code></li>
</ul>
<p>If <code>&quot; World&quot;</code> were lost, the receiver would keep saying <code>ACK=6</code>, and the sender would know exactly what to resend.</p>
<h2 id="how-tcp-keeps-its-promises">How TCP Keeps Its Promises<a class="heading-anchor" href="#how-tcp-keeps-its-promises" aria-label="Link to this section">#</a></h2>
<table>
<thead>
<tr>
<th>Mechanism</th>
<th>How It Works</th>
</tr>
</thead>
<tbody><tr>
<td><strong>Sequence Numbers</strong></td>
<td>Each byte gets a number. Receiver reorders out-of-order packets.</td>
</tr>
<tr>
<td><strong>Acknowledgments (ACKs)</strong></td>
<td>Receiver confirms receipt. Missing ACK triggers retransmission.</td>
</tr>
<tr>
<td><strong>Checksum</strong></td>
<td>Detects corrupted data. Bad packets are discarded and resent.</td>
</tr>
<tr>
<td><strong>Retransmission Timer</strong></td>
<td>If no ACK arrives in time, sender resends the segment.</td>
</tr>
<tr>
<td><strong>Flow Control</strong></td>
<td>Receiver advertises window size to prevent overwhelming it.</td>
</tr>
</tbody></table>
<h2 id="closing-takes-four-messages-not-three">Closing Takes Four Messages, Not Three<a class="heading-anchor" href="#closing-takes-four-messages-not-three" aria-label="Link to this section">#</a></h2>
<p>Either side can start closing, using the <strong>FIN</strong> (finish) flag. Each direction is closed separately, so it takes four messages:</p>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang"></span>
        <button type="button" class="code-copy">Copy</button>
      </div>
      <pre class="shiki"><code>    Client                    Server
       |                         |
       |-------- FIN -----------&gt;|   1. Client: &quot;I'm done sending&quot;
       |&lt;------- ACK ------------|   2. Server: &quot;Got it&quot;
       |                         |
       |&lt;------- FIN ------------|   3. Server: &quot;I'm done too&quot;
       |-------- ACK -----------&gt;|   4. Client: &quot;Got it, closing&quot;
       |                         |
    CLOSED                    CLOSED</code></pre>
    </div><p><strong>Example:</strong> closing an HTTP connection</p>
<ol>
<li>The browser is done sending → sends <strong>FIN</strong></li>
<li>The server acknowledges with <strong>ACK</strong></li>
<li>The server finishes its response → sends its own <strong>FIN</strong></li>
<li>The browser sends the final <strong>ACK</strong> → both sides close</li>
</ol>
<p>The side that closed first then waits in a <strong>TIME_WAIT</strong> state, for twice the maximum segment lifetime (60 seconds on Linux), so any delayed packets from the old connection die out before the same address and port are reused.</p>
<hr>
<p>Three packets with no data in them look like overhead. They&#39;re what lets TCP spot a missing byte, put segments back in order and throw away duplicates. Every guarantee TCP makes starts with two numbers agreed in that handshake.</p>
