23:T1790,<p>You type <code>spark-submit</code>, press enter, and some time later the result shows up. Your code ran somewhere in the middle of that, but most of what happened wasn&#39;t your code at all.</p>
<blockquote>
<p>Before your first line of Spark code runs, a driver has to be placed, executors have to be requested, and a cluster has to agree to give them to you.</p>
</blockquote>
<p>This post follows a Spark application from the outside, in four steps: the request, the launch, the execution and the completion. It assumes <strong>cluster mode</strong>, where the driver runs inside the cluster; if that&#39;s new, read <a href="/blog/spark-execution-modes">Spark Execution Modes</a> first.</p>
<!-- truncate -->

<h2 id="1-the-request-spark-submit-asks-for-a-driver">1. The Request: spark-submit Asks for a Driver<a class="heading-anchor" href="#1-the-request-spark-submit-asks-for-a-driver" aria-label="Link to this section">#</a></h2>
<p>Everything starts on your machine. <code>spark-submit</code> packages up what to run and sends a request to the <strong>cluster manager</strong> (YARN, Kubernetes, or Spark&#39;s standalone master): &quot;please start a driver for this application&quot;.</p>
<p><img src="/posts/2025-02-07-spark-application-architecture-outside/assets/requesting_resources.gif" alt="Requesting Resources" loading="lazy" /></p>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang"></span>
        <button type="button" class="code-copy">Copy</button>
      </div>
      <pre class="shiki"><code>./bin/spark-submit \
  --class &lt;main-class&gt; \
  --master &lt;master-url&gt; \
  --deploy-mode cluster \
  --conf &lt;key&gt;=&lt;value&gt; \
  ... # other options
  &lt;application-jar&gt; \
  [application-arguments]</code></pre>
    </div><p>The arguments describe the application, not the work:</p>
<ul>
<li><code>--class</code>: the main class of the application</li>
<li><code>--master</code>: which cluster manager to talk to (<code>yarn</code>, <code>k8s://…</code>, <code>spark://…</code>, or <code>local</code> for no cluster)</li>
<li><code>--deploy-mode</code>: where the driver runs, <code>cluster</code> or <code>client</code></li>
<li><code>--conf</code>: configuration such as executor count, memory and cores</li>
<li>the application JAR (or Python file) and its arguments</li>
</ul>
<p>At this point no Spark code has run. Your machine has only asked for a driver.</p>
<h2 id="2-the-launch-the-driver-asks-for-executors">2. The Launch: The Driver Asks for Executors<a class="heading-anchor" href="#2-the-launch-the-driver-asks-for-executors" aria-label="Link to this section">#</a></h2>
<p>The cluster manager starts the driver process on one of the cluster&#39;s nodes, and the driver starts running your code.</p>
<p>One of the first things your code does is create a <code>SparkSession</code>. That&#39;s the moment the driver turns to the cluster manager again, this time asking for <strong>executors</strong>, with the number, memory and cores you passed to <code>spark-submit</code>. The cluster manager launches the executor processes across the cluster and tells the driver where they are.</p>
<p><img src="/posts/2025-02-07-spark-application-architecture-outside/assets/launch.gif" alt="Launch Application" loading="lazy" /></p>
<p>Now there&#39;s a driver and a set of executors, and the application finally has somewhere to run.</p>
<h2 id="3-execution-the-driver-schedules-executors-report-back">3. Execution: The Driver Schedules, Executors Report Back<a class="heading-anchor" href="#3-execution-the-driver-schedules-executors-report-back" aria-label="Link to this section">#</a></h2>
<p>With executors running, the driver goes through your code. Each action becomes a job, each job is split into stages and tasks (see <a href="/blog/spark-job-anatomy">Under the hood of a Spark job</a>), and the driver sends those tasks to the executors.</p>
<p>The executors run them, move data between each other when a shuffle needs it, and report each task&#39;s success or failure back to the driver. The cluster manager isn&#39;t involved here at all: it only hands out resources.</p>
<p><img src="/posts/2025-02-07-spark-application-architecture-outside/assets/execution.gif" alt="Execution" loading="lazy" /></p>
<h2 id="4-completion-the-cluster-manager-cleans-up">4. Completion: The Cluster Manager Cleans Up<a class="heading-anchor" href="#4-completion-the-cluster-manager-cleans-up" aria-label="Link to this section">#</a></h2>
<p>When your code finishes, the driver exits with either success or failure. The cluster manager then shuts down the executors that belonged to that driver and frees their resources for the next application.</p>
<p><img src="/posts/2025-02-07-spark-application-architecture-outside/assets/completion.gif" alt="Completion" loading="lazy" /></p>
<p>To find out whether the application succeeded, ask the cluster manager (for example, the YARN ResourceManager UI), not your terminal: in cluster mode, your machine stopped being involved after step 1.</p>
<h2 id="the-whole-trip">The Whole Trip<a class="heading-anchor" href="#the-whole-trip" aria-label="Link to this section">#</a></h2>
<table>
<thead>
<tr>
<th>Step</th>
<th>Who acts</th>
<th>What happens</th>

<p>So when a job is &quot;slow to start&quot;, it might not be your code at all. It might still be at step 1 or 2, waiting for the cluster to hand over a driver or executors.</p>
