21:T1843,<p>A class in <a href="/#work">Move</a>, the gym management app I&#39;m building, has 10 spots. Nine are booked. Two members open the app and tap &quot;Book&quot; at the same moment.</p>
<p>Exactly one of them should get the spot. The other should see &quot;This session is full&quot;. If both get in, the coach walks into a class with 11 people and 10 bikes.</p>
<p>This post covers how Move prevents that with a Postgres row lock, a reproduction of the race without the lock, and two mistakes around that lock: one that could freeze every booking at once, and one that quietly makes unrelated bookings wait for each other.</p>
<aside class="callout callout-tldr">
      <p class="callout-title">TL;DR</p>
      <div class="callout-body"><p><strong>Problem:</strong> two people booking the last spot at the same moment can both get in, because each checks the count before the other has written.</p>
<p><strong>Fix:</strong> lock the class&#39;s row with <code>SELECT … FOR UPDATE</code> inside the booking transaction, so the second request waits and sees the real count. Keep the lock short, and lock only the table you&#39;re changing (<code>FOR UPDATE OF sessions</code>).</p>
</div>
    </aside>

<h2 id="the-obvious-code-has-a-race-condition">The obvious code has a race condition<a class="heading-anchor" href="#the-obvious-code-has-a-race-condition" aria-label="Link to this section">#</a></h2>
<p>The natural way to write a booking looks like this:</p>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang">TypeScript</span>
        <button type="button" class="code-copy">Copy</button>
      </div>
      <pre class="shiki github-light-high-contrast" tabindex="0"><code><span class="line"><span style="color:#A0111F">const</span><span style="color:#023B95"> session</span><span style="color:#A0111F"> =</span><span style="color:#A0111F"> await</span><span style="color:#0E1116"> db</span></span>
<span class="line"><span style="color:#0E1116">  .</span><span style="color:#622CBC">select</span><span style="color:#0E1116">()</span></span>
<span class="line"><span style="color:#0E1116">  .</span><span style="color:#622CBC">from</span><span style="color:#0E1116">(sessions)</span></span>
<span class="line"><span style="color:#0E1116">  .</span><span style="color:#622CBC">where</span><span style="color:#0E1116">(</span><span style="color:#622CBC">eq</span><span style="color:#0E1116">(sessions.id, sessionId));</span></span>
<span class="line"><span style="color:#A0111F">if</span><span style="color:#0E1116"> (session.bookedCount </span><span style="color:#A0111F">>=</span><span style="color:#0E1116"> session.capacity) {</span></span>
<span class="line"><span style="color:#A0111F">  throw</span><span style="color:#A0111F"> new</span><span style="color:#622CBC"> SessionFullError</span><span style="color:#0E1116">();</span></span>
<span class="line"><span style="color:#0E1116">}</span></span>
<span class="line"><span style="color:#A0111F">await</span><span style="color:#622CBC"> insertBooking</span><span style="color:#0E1116">(clientId, sessionId);</span></span>
<span class="line"><span style="color:#A0111F">await</span><span style="color:#0E1116"> db</span></span>
<span class="line"><span style="color:#0E1116">  .</span><span style="color:#622CBC">update</span><span style="color:#0E1116">(sessions)</span></span>
<span class="line"><span style="color:#0E1116">  .</span><span style="color:#622CBC">set</span><span style="color:#0E1116">({ bookedCount: </span><span style="color:#622CBC">sql</span><span style="color:#032563">`booked_count + 1`</span><span style="color:#0E1116"> })</span></span>
<span class="line"><span style="color:#0E1116">  .</span><span style="color:#622CBC">where</span><span style="color:#0E1116">(</span><span style="color:#622CBC">eq</span><span style="color:#0E1116">(sessions.id, sessionId));</span></span></code></pre>
    </div><p>It reads the count, checks it, then writes. That&#39;s a <strong>check-then-act</strong> pattern, and it breaks the moment two requests interleave: both read 9, both decide there&#39;s room, both insert.</p>
<p>You don&#39;t need to take my word for it. I ran two transactions against Postgres 16 that do exactly this, with a one-second pause between the check and the write to make the overlap certain:</p>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang"></span>
        <button type="button" class="code-copy">Copy</button>
      </div>
      <pre class="shiki"><code>B booked (saw 9/10)
A booked (saw 9/10)
final: 11/10</code></pre>
    </div><p>Both requests saw 9 of 10 and both booked. The class is overbooked, and no error was raised anywhere.</p>
<aside class="callout callout-warning">
      <p class="callout-title">Warning</p>
      <div class="callout-body"><p>Wrapping the code in a transaction doesn&#39;t fix this on its own. At Postgres&#39;s default isolation level (<code>READ COMMITTED</code>), a plain <code>SELECT</code> takes no lock, so two transactions can still read the same count and both act on it.</p>
</div>
    </aside>

<h2 id="the-fix-lock-the-row-with-select-for-update">The fix: lock the row with SELECT … FOR UPDATE<a class="heading-anchor" href="#the-fix-lock-the-row-with-select-for-update" aria-label="Link to this section">#</a></h2>
<p><code>SELECT … FOR UPDATE</code> reads a row <strong>and locks it</strong> until the transaction ends. Any other transaction that tries to lock the same row waits until the first one commits or rolls back. Then it reads the row again and sees the new value.</p>
<p>Same experiment, with <code>FOR UPDATE</code> added to the read:</p>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang"></span>
        <button type="button" class="code-copy">Copy</button>
      </div>
      <pre class="shiki"><code>B booked (saw 9/10)
A rejected: full (saw 10/10)
final: 10/10</code></pre>
    </div><p>B got the lock first and booked. A waited, then read the real count of 10 and was turned away. Exactly one booking, no matter how the requests are timed.</p>

    </div><p>Three rules hold this together.</p>
<h3 id="1-always-take-locks-in-the-same-order">1. Always take locks in the same order<a class="heading-anchor" href="#1-always-take-locks-in-the-same-order" aria-label="Link to this section">#</a></h3>
<p>Every booking locks the <strong>client first, then the session, then the credit lot</strong> it spends from. If one request locked session → client while another locked client → session, each could end up holding the lock the other needs. That&#39;s a deadlock, and Postgres resolves it by killing one of the transactions.</p>
<p>Locking the client also covers a quieter case: a member double-tapping &quot;Book&quot; on two different classes that overlap in time. Their two requests now run one after another, so the overlap check in the second one sees the first booking.</p>
<h3 id="2-nothing-slow-happens-while-the-lock-is-held">2. Nothing slow happens while the lock is held<a class="heading-anchor" href="#2-nothing-slow-happens-while-the-lock-is-held" aria-label="Link to this section">#</a></h3>
<p>Everything inside the transaction is a fast local Postgres statement: about eight of them per booking, including the credit deduction and the audit log entry. There&#39;s no payment gateway call, no HTTP request and no email under the lock.</p>
<p>Confirmation emails are sent <strong>after</strong> the transaction commits. If the email provider takes three seconds to respond, the next person booking that class doesn&#39;t wait three seconds for the lock.</p>
<h3 id="3-every-check-that-depends-on-shared-state-runs-after-the-lock">3. Every check that depends on shared state runs after the lock<a class="heading-anchor" href="#3-every-check-that-depends-on-shared-state-runs-after-the-lock" aria-label="Link to this section">#</a></h3>
<p>The capacity check, the &quot;has the class already started?&quot; check, and the overlap check all run after the locks are taken. A check done before locking is a check against data that may already be out of date.</p>
<h2 id="mistake-1-a-second-connection-inside-the-transaction-can-freeze-every-booking">Mistake 1: a second connection inside the transaction can freeze every booking<a class="heading-anchor" href="#mistake-1-a-second-connection-inside-the-transaction-can-freeze-every-booking" aria-label="Link to this section">#</a></h2>
<p>Inside a transaction, one query that uses the global client instead of the transaction handle can hang your whole app. It&#39;s a one-word mistake, and it usually hides in a helper function.</p>
<p>Charging for a booking is a good example. A helper, <code>pickCreditLot</code>, decides which of the member&#39;s credit packs to spend from (the one expiring soonest), and runs its query like this:</p>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang">TypeScript</span>
        <button type="button" class="code-copy">Copy</button>
      </div>
      <pre class="shiki github-light-high-contrast" tabindex="0"><code><span class="line"><span style="color:#66707B">// inside chargeFor(tx, ...), while the booking transaction holds its locks</span></span>
<span class="line"><span style="color:#A0111F">const</span><span style="color:#023B95"> candidates</span><span style="color:#A0111F"> =</span><span style="color:#A0111F"> await</span><span style="color:#0E1116"> db.</span><span style="color:#622CBC">select</span><span style="color:#0E1116">().</span><span style="color:#622CBC">from</span><span style="color:#0E1116">(creditLots).</span><span style="color:#622CBC">where</span><span style="color:#0E1116">(</span><span style="color:#66707B">/* ... */</span><span style="color:#0E1116">);</span></span></code></pre>
    </div><p>Note <code>db</code>, not <code>tx</code>. <code>db</code> is the connection pool, so this query borrows a <strong>second</strong> connection while the transaction is still holding its first one.</p>
<p>With a pool of 10 connections, that&#39;s a trap:</p>
<ol>
<li>Ten members book at once. Each booking transaction takes one connection: the pool is now empty.</li>
<li>Each of them reaches <code>pickCreditLot</code> and asks the pool for a second connection.</li>
<li>None is free, and none will be: every connection belongs to a transaction that&#39;s waiting for another connection.</li>
</ol>
<p>Every booking hangs at once, and without a timeout, nothing ever breaks the wait. Postgres can&#39;t detect it as a deadlock either, because Postgres never sees the waiting: it happens in the pool, inside the application.</p>
<p>The fix is to pass the transaction through:</p>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang">TypeScript</span>
        <button type="button" class="code-copy">Copy</button>
      </div>

<div class="code-block">
      <div class="code-head">

        <button type="button" class="code-copy">Copy</button>

<h2 id="mistake-2-for-update-locks-every-table-in-the-join">Mistake 2: FOR UPDATE locks every table in the join<a class="heading-anchor" href="#mistake-2-for-update-locks-every-table-in-the-join" aria-label="Link to this section">#</a></h2>
<p>In Postgres, <code>FOR UPDATE</code> without a table list locks the matching rows in <strong>every table in the query</strong>, not just the one you meant to lock. Add a join for convenience and you&#39;ve widened the lock without changing a word of the locking code.</p>
<p>It&#39;s an easy join to write. Reading a class&#39;s row together with its type, to get the credit type in one query, looks like this:</p>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang">TypeScript</span>
        <button type="button" class="code-copy">Copy</button>
      </div>
      <pre class="shiki github-light-high-contrast" tabindex="0"><code><span class="line"><span style="color:#0E1116">.</span><span style="color:#622CBC">from</span><span style="color:#0E1116">(sessions)</span></span>
<span class="line"><span style="color:#0E1116">.</span><span style="color:#622CBC">innerJoin</span><span style="color:#0E1116">(sessionTypes, </span><span style="color:#622CBC">eq</span><span style="color:#0E1116">(sessions.sessionTypeId, sessionTypes.id))</span></span>
<span class="line"><span style="color:#0E1116">.</span><span style="color:#622CBC">where</span><span style="color:#0E1116">(</span><span style="color:#622CBC">eq</span><span style="color:#0E1116">(sessions.id, sessionId))</span></span>
<span class="line"><span style="color:#0E1116">.</span><span style="color:#622CBC">for</span><span style="color:#0E1116">(</span><span style="color:#032563">"update"</span><span style="color:#0E1116">);</span></span></code></pre>
    </div><p>Drizzle turns that into a plain <code>FOR UPDATE</code>, so it locks the session row <strong>and</strong> the <code>session_types</code> row for &quot;HIIT&quot;. Every HIIT class shares that one row.</p>
<p>So two members booking <strong>different</strong> HIIT classes (the 7am and the 6pm) wait for each other, because both transactions want the same <code>session_types</code> row. A lock meant to protect one class now serialises every booking of that class type.</p>
<p>You can see it with two transactions, the second with a one-second <code>lock_timeout</code>:</p>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang"></span>
        <button type="button" class="code-copy">Copy</button>
      </div>
      <pre class="shiki"><code>-- for update: A locks the 7am HIIT, B wants the 6pm HIIT
B: ERROR:  canceling statement due to lock timeout
B: CONTEXT:  while locking tuple (0,1) in relation &quot;session_types&quot;

-- for update of s
B: 2
B took 0.03s</code></pre>
    </div><p>The fix is to name the table to lock. In SQL that&#39;s <code>FOR UPDATE OF sessions</code>; in Drizzle:</p>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang">TypeScript</span>
        <button type="button" class="code-copy">Copy</button>
      </div>
      <pre class="shiki github-light-high-contrast" tabindex="0"><code><span class="line"><span style="color:#0E1116">.</span><span style="color:#622CBC">for</span><span style="color:#0E1116">(</span><span style="color:#032563">"update"</span><span style="color:#0E1116">, { of: sessions });</span></span></code></pre>
    </div><p>The lesson: <strong>whenever a <code>FOR UPDATE</code> query has a join, name the table you mean to lock.</strong> Under light traffic the extra lock costs milliseconds, so tests and staging won&#39;t show it. It surfaces when traffic peaks, as unrelated requests queueing behind each other, and nothing in the code looks wrong unless you know the rule.</p>
<h2 id="dont-let-the-lock-be-your-only-guard">Don&#39;t let the lock be your only guard<a class="heading-anchor" href="#dont-let-the-lock-be-your-only-guard" aria-label="Link to this section">#</a></h2>
<p>A row lock prevents overbooking only as long as every code path takes it. Two more pieces make the design hold up when something goes wrong.</p>
<p><strong>Put a constraint under the lock.</strong> If someone later removes <code>.for(&quot;update&quot;)</code> by accident, or writes a new booking path that forgets it, nothing stops an overbook. A <code>CHECK</code> constraint makes the database itself refuse the invalid state:</p>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang">SQL</span>
        <button type="button" class="code-copy">Copy</button>
      </div>
      <pre class="shiki github-light-high-contrast" tabindex="0"><code><span class="line"><span style="color:#A0111F">ALTER</span><span style="color:#A0111F"> TABLE</span><span style="color:#A0111F"> sessions</span></span>
<span class="line"><span style="color:#A0111F">  ADD</span><span style="color:#A0111F"> CONSTRAINT</span><span style="color:#0E1116"> sessions_booked_count_within_capacity</span></span>
<span class="line"><span style="color:#A0111F">  CHECK</span><span style="color:#0E1116"> (booked_count </span><span style="color:#A0111F">&#x3C;=</span><span style="color:#0E1116"> capacity);</span></span></code></pre>
    </div><p>Now the eleventh booking fails with a constraint error instead of silently succeeding. The lock keeps things correct; the constraint catches the day the lock is missing.</p>
<p><strong>Expect a popular row to become a queue.</strong> Every booking for the same class takes the same lock, even when 8 spots are left. If 200 people try to book the 7am class the second it opens, they run one at a time. With a lock held for a few milliseconds that&#39;s acceptable, but the wait is real, and a slow transaction makes it worse. Set a short <code>lock_timeout</code> on the booking transaction so a request that waits too long fails fast and the client can retry, instead of hanging until <code>statement_timeout</code>.</p>
<h2 id="other-ways-to-prevent-double-booking">Other ways to prevent double booking<a class="heading-anchor" href="#other-ways-to-prevent-double-booking" aria-label="Link to this section">#</a></h2>
<p><code>SELECT … FOR UPDATE</code> isn&#39;t the only option. Here&#39;s how the common approaches compare:</p>
<table>
<thead>
<tr>
<th>Approach</th>
<th>How it works</th>
<th>Good for</th>
<th>Watch out for</th>
</tr>
</thead>
<tbody><tr>
<td><code>SELECT … FOR UPDATE</code></td>
<td>Lock the row, check, write</td>
<td>Several checks before the write (capacity, timing, credits)</td>
<td>Hot rows queue; lock only what you need</td>
</tr>
<tr>
<td>Conditional <code>UPDATE</code></td>
<td><code>UPDATE sessions SET booked_count = booked_count + 1 WHERE id = $1 AND booked_count &lt; capacity RETURNING id</code></td>
<td>A single counter with one rule</td>
<td>Hard to fit more checks into one statement</td>
</tr>
<tr>
<td><code>SERIALIZABLE</code> isolation</td>
<td>Postgres aborts transactions that would conflict</td>
<td>Complex invariants across many rows</td>
<td>Every caller must retry on serialization errors</td>
</tr>
<tr>
<td><code>CHECK</code> constraint</td>
<td>The database rejects an invalid state</td>
<td>A backstop under any of the above</td>
<td>Only checks one row; turns a race into an error, not a queue</td>
</tr>
</tbody></table>
<p>Move uses <code>FOR UPDATE</code> because a booking checks a lot more than capacity: whether the class has started, whether the member&#39;s membership is paused, whether they have a valid credit, whether it overlaps another booking. All of those need a consistent view of the data, and a row lock gives that with ordinary code.</p>
<h2 id="frequently-asked-questions">Frequently asked questions<a class="heading-anchor" href="#frequently-asked-questions" aria-label="Link to this section">#</a></h2>
<h3 id="how-do-i-prevent-double-booking-in-postgres">How do I prevent double booking in Postgres?<a class="heading-anchor" href="#how-do-i-prevent-double-booking-in-postgres" aria-label="Link to this section">#</a></h3>
<p>Run the capacity check and the insert in one transaction, and read the row with <code>SELECT … FOR UPDATE</code> so concurrent bookings for the same slot wait for each other. Add a <code>CHECK (booked_count &lt;= capacity)</code> constraint as a backstop.</p>
<h3 id="does-a-transaction-alone-prevent-race-conditions">Does a transaction alone prevent race conditions?<a class="heading-anchor" href="#does-a-transaction-alone-prevent-race-conditions" aria-label="Link to this section">#</a></h3>
<p>No. At the default <code>READ COMMITTED</code> isolation level, two transactions can read the same row and both act on the stale value. You need a row lock, a conditional update, or <code>SERIALIZABLE</code> isolation.</p>
<h3 id="does-select-for-update-lock-the-whole-table">Does SELECT FOR UPDATE lock the whole table?<a class="heading-anchor" href="#does-select-for-update-lock-the-whole-table" aria-label="Link to this section">#</a></h3>
<p>No, only the rows the query returns. But with a join, it locks the matching rows in <strong>every</strong> joined table unless you write <code>FOR UPDATE OF &lt;table&gt;</code>.</p>
<h3 id="how-do-i-use-for-update-in-drizzle-orm">How do I use FOR UPDATE in Drizzle ORM?<a class="heading-anchor" href="#how-do-i-use-for-update-in-drizzle-orm" aria-label="Link to this section">#</a></h3>
<p>Call <code>.for(&quot;update&quot;)</code> on the select query inside <code>db.transaction()</code>. Pass <code>{ of: table }</code> as the second argument to lock only one table in a join: <code>.for(&quot;update&quot;, { of: sessions })</code>.</p>
<h2 id="wrapping-up">Wrapping up<a class="heading-anchor" href="#wrapping-up" aria-label="Link to this section">#</a></h2>
<p>Preventing double bookings comes down to one line: lock the row before you check it. The interesting part is everything around that line: keeping the lock short, taking locks in the same order, never borrowing a second connection inside the transaction, and locking only the table you mean to.</p>
<p>If you&#39;re building something similar, try the race yourself: two <code>psql</code> sessions, a <code>pg_sleep(1)</code> between the check and the write, and watch the count go to 11.</p>
