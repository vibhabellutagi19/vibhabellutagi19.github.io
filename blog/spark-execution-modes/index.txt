21:T207f,<p>Submit a Spark job from your laptop, close the lid, and the job dies. Submit the same job with one flag changed, <code>--deploy-mode cluster</code>, close the lid, and it keeps running.</p>
<p>Nothing about the code changed. What changed is where one process, the <strong>driver</strong>, runs.</p>
<blockquote>
<p>An execution mode decides one thing: where the driver lives.</p>
</blockquote>
<p>Spark has three modes: cluster, client and local. This post covers the three processes behind every Spark application, then what each mode does with them.</p>
<!--truncate-->

<h2 id="three-processes-run-every-spark-application">Three Processes Run Every Spark Application<a class="heading-anchor" href="#three-processes-run-every-spark-application" aria-label="Link to this section">#</a></h2>
<ol>
<li><strong>The Spark Driver</strong><ul>
<li>The driver is the <Highlight color="#3e6980">controller of the execution</Highlight>. It keeps track of the application&#39;s state: which executors exist and which tasks they&#39;re running.</li>
<li>It asks the cluster manager for resources and schedules tasks on the executors.</li>
<li>It&#39;s just a process on a machine. If that process dies, the whole application dies with it.</li>
</ul>
</li>
<li><strong>The Spark Executors</strong><ul>
<li>Executors are <Highlight color="#3e6980">the processes that run the actual tasks</Highlight>, as assigned by the driver.</li>
<li>Each executor takes tasks from the driver, runs them, and reports their status and results back.</li>
</ul>
</li>
<li><strong>The Cluster Manager</strong><ul>
<li>The cluster manager <Highlight color="#3e6980">maintains the cluster of machines</Highlight> that will run your Spark application(s), for example YARN or Kubernetes.</li>
<li>Somewhat confusingly, a cluster manager has its own &quot;driver&quot; (sometimes called master) and &quot;worker&quot; abstractions.</li>
<li>The difference is that these are tied to physical machines, not processes as they are in Spark.</li>
</ul>
</li>
</ol>
<p><img src="/posts/2025-02-06-spark-execution-modes/assets/cluster_manager.png" alt="Cluster Manager" loading="lazy" /></p>
<h3 id="think-of-it-as-a-restaurant-kitchen">Think of It as a Restaurant Kitchen<a class="heading-anchor" href="#think-of-it-as-a-restaurant-kitchen" aria-label="Link to this section">#</a></h3>
<ol>
<li><strong>Spark Driver (Head Chef)</strong>: manages the kitchen, assigns tasks to the cooks, and makes sure every dish is prepared correctly.</li>
<li><strong>Spark Executors (Cooks)</strong>: prepare the dishes following the head chef&#39;s instructions and report back when each one is ready.</li>
<li><strong>Cluster Manager (Restaurant Manager)</strong>: makes sure the kitchen has enough staff, ingredients and equipment, and handles several kitchens&#39; orders at once.</li>
</ol>
<p>The execution mode answers one question: is the head chef standing in the kitchen, or giving instructions over the phone from home?</p>
<h2 id="cluster-mode-the-driver-lives-inside-the-cluster">Cluster Mode: The Driver Lives Inside the Cluster<a class="heading-anchor" href="#cluster-mode-the-driver-lives-inside-the-cluster" aria-label="Link to this section">#</a></h2>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang">Bash</span>
        <button type="button" class="code-copy">Copy</button>
      </div>
      <pre class="shiki github-light-high-contrast" tabindex="0"><code><span class="line"><span style="color:#702C00">spark-submit</span><span style="color:#023B95"> --deploy-mode</span><span style="color:#032563"> cluster</span><span style="color:#032563"> ...</span></span></code></pre>
    </div><ol>
<li>You submit a JAR or Python script to the cluster manager.</li>
<li>The cluster manager launches both the driver and the executors on worker nodes inside the cluster.</li>
<li>The driver runs on one worker node; executors run on others.</li>
<li>The cluster manager manages and monitors all of the application&#39;s processes.</li>
</ol>
<p><img src="/posts/2025-02-06-spark-execution-modes/assets/cluster_mode.gif" alt="Cluster Mode" loading="lazy" /></p>
<p>Once the job is submitted, your machine is no longer involved. Close the laptop, lose the VPN, and the job carries on.</p>
<h2 id="client-mode-the-driver-lives-on-your-machine">Client Mode: The Driver Lives on Your Machine<a class="heading-anchor" href="#client-mode-the-driver-lives-on-your-machine" aria-label="Link to this section">#</a></h2>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang">Bash</span>
        <button type="button" class="code-copy">Copy</button>
      </div>
      <pre class="shiki github-light-high-contrast" tabindex="0"><code><span class="line"><span style="color:#702C00">spark-submit</span><span style="color:#023B95"> --deploy-mode</span><span style="color:#032563"> client</span><span style="color:#032563"> ...</span></span></code></pre>
    </div><ol>
<li>The driver runs on the machine that submitted the application, often called a <strong>gateway machine</strong> or <strong>edge node</strong>.</li>
<li>The cluster manager still launches the executors on worker nodes inside the cluster.</li>
<li>The driver talks to those executors over the network from outside the cluster.</li>
</ol>
<p><img src="/posts/2025-02-06-spark-execution-modes/assets/client_mode.gif" alt="Client Mode" loading="lazy" /></p>
<p>This is what makes interactive work possible: <code>spark-shell</code> and notebooks run in client mode, so results come straight back to your screen. It&#39;s also why the job dies with your laptop: the driver was running on it.</p>
<h2 id="local-mode-everything-runs-on-one-machine">Local Mode: Everything Runs on One Machine<a class="heading-anchor" href="#local-mode-everything-runs-on-one-machine" aria-label="Link to this section">#</a></h2>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang">Bash</span>
        <button type="button" class="code-copy">Copy</button>
      </div>
      <pre class="shiki github-light-high-contrast" tabindex="0"><code><span class="line"><span style="color:#702C00">spark-submit</span><span style="color:#023B95"> --master</span><span style="color:#032563"> "local[*]"</span><span style="color:#032563"> ...</span></span></code></pre>
    </div><ol>
<li>The driver and the executors all run in a single process on one machine.</li>
<li>Parallelism comes from threads (<code>local[*]</code> uses one per core), not from multiple nodes.</li>
<li>No cluster manager is needed.</li>
<li>It&#39;s for learning, testing and quick experiments on small data, not for production.</li>
</ol>
<h2 id="client-vs-cluster-at-a-glance">Client vs Cluster at a Glance<a class="heading-anchor" href="#client-vs-cluster-at-a-glance" aria-label="Link to this section">#</a></h2>
<table>
<thead>
<tr>
<th></th>
<th><strong>Client Mode</strong></th>
<th><strong>Cluster Mode</strong></th>
</tr>
</thead>
<tbody><tr>
<td><strong>Driver runs on</strong></td>
<td>The submitting machine</td>
<td>A worker node in the cluster</td>
</tr>
<tr>
<td><strong>Best for</strong></td>
<td>Interactive use (development, debugging)</td>
<td>Production jobs, large-scale deployments</td>
</tr>
<tr>
<td><strong>Latency</strong></td>
<td>Lower latency for small tasks</td>
<td>Slightly higher due to internal resource allocation</td>
</tr>
<tr>
<td><strong>Example Use Case</strong></td>
<td>Testing and interactive Spark shells</td>
<td>Scheduled batch jobs or long-running Spark applications</td>
</tr>
<tr>
<td><strong>Advantages</strong></td>
<td>Easier to debug and monitor from client machine</td>
<td>More reliable and scalable for production workloads</td>
</tr>
<tr>
<td><strong>Disadvantages</strong></td>
<td>The job dies if the client machine disconnects</td>
<td>More setup needed, harder to debug directly</td>
</tr>
</tbody></table>
<p>If your job has to outlive your terminal session, it needs cluster mode. If you want to see results as you type, it needs client mode.</p>
