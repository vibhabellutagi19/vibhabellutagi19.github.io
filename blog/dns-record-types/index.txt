Pointing it at your website takes one DNS record. Receiving email at <code>hello@vibhavari.com</code> takes a different one. Proving to Google that you own the domain takes a third.</p>
<p>One domain, three jobs, three different records.</p>
<blockquote>
<p>A domain isn&#39;t one address. It&#39;s a set of records, and each record answers a different question about it.</p>
</blockquote>
<p>In <a href="/blog/how-dns-resolution-works">How DNS Resolution Works</a> we followed a lookup down to the authoritative server that &quot;holds the records&quot;. This post is about those records: the six types you&#39;ll actually use, what each one does, and when you need it.</p>
<h2 id="one-domain-many-jobs">One Domain, Many Jobs<a class="heading-anchor" href="#one-domain-many-jobs" aria-label="Link to this section">#</a></h2>
<p>Think about a contact in your phone. You don&#39;t store just one piece of information: you save their mobile number, work number, email, maybe their home address. Each one serves a different purpose, but they all belong to the same person.</p>
<p>DNS records work the same way. Your website needs to load. Emails need to arrive. Subdomains need to work. Ownership needs to be verified. A single IP address can&#39;t express all of that, so DNS stores <strong>records</strong>: different types of entries that tell the internet how to handle different requests for your domain.</p>
<h2 id="a-record-name-ipv4-address">A Record: Name → IPv4 Address<a class="heading-anchor" href="#a-record-name-ipv4-address" aria-label="Link to this section">#</a></h2>
<p>A → &quot;Address&quot;, the most fundamental record type. It maps a domain to an IPv4 address. When a <a href="/blog/how-dns-resolution-works">DNS resolver</a> asks for a domain&#39;s address, the A record returns the 32-bit IPv4 address attached to it.</p>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang"></span>
        <button type="button" class="code-copy">Copy</button>
      </div>
      <pre class="shiki"><code>example.com.    3600    IN    A           93.184.216.34</code></pre>
    </div><ul>
<li>TTL (Time To Live): 3600 seconds</li>
<li>Class: IN (Internet)</li>
<li>Type: A</li>
<li>Value: IPv4 address</li>
</ul>
<p>Most websites have a single A record, but some high-traffic sites have several, and resolvers rotate between them as a simple form of load balancing (round robin).</p>
<p>Imagine you&#39;re looking up &quot;Krishna&#39;s Kapi Shop&quot; in a city directory. The A record is the entry that says &quot;Krishna&#39;s Kapi Shop → 742 Evergreen Terrace.&quot; Now you know exactly which building (server) to go to. Without it, you know the name but can&#39;t find the place.</p>
<h4 id="when-and-why-used">When and Why Used<a class="heading-anchor" href="#when-and-why-used" aria-label="Link to this section">#</a></h4>
<ul>
<li><strong>Primary use</strong>: Pointing your domain to your web server</li>
<li><strong>When</strong>: Every website needs at least one A record for the root domain (or an AAAA record for IPv6)</li>
<li><strong>Why</strong>: Without it, browsers can&#39;t find your website; they need the IP address to connect</li>
<li><strong>Example scenario</strong>: You host your website on a server at IP 203.0.113.50. You create an A record so <code>mysite.com</code> points to that IP</li>
</ul>
<h2 id="aaaa-record-name-ipv6-address">AAAA Record: Name → IPv6 Address<a class="heading-anchor" href="#aaaa-record-name-ipv6-address" aria-label="Link to this section">#</a></h2>
<p>An AAAA record maps a domain name to a 128-bit IPv6 address. It works exactly like an A record, but for the newer IPv6 addressing scheme. The name comes from IPv6 addresses being four times larger than IPv4 (128 bits vs 32 bits).</p>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang"></span>
        <button type="button" class="code-copy">Copy</button>
      </div>
      <pre class="shiki"><code>example.com. 3600 IN AAAA 2001:0db8:85a3:0000:0000:8a2e:0370:7334</code></pre>
    </div><p>Think of phone numbers. The old system had short local numbers (IPv4), and we ran out. Now there are longer numbers with country codes and more digits (IPv6). Both get you to the same place; they&#39;re just different numbering systems.</p>
<h4 id="when-and-why-used-1">When and Why Used<a class="heading-anchor" href="#when-and-why-used-1" aria-label="Link to this section">#</a></h4>
<ul>
<li><strong>Primary use</strong>: Making your services reachable over IPv6</li>
<li><strong>When</strong>: Increasingly necessary as IPv4 addresses run out; major sites have both A and AAAA records</li>
<li><strong>Why</strong>: Some networks are IPv6-only, and IPv6 clients can reach you directly without translation</li>
<li><strong>Example scenario</strong>: Your hosting provider gives you an IPv6 address. You add an AAAA record so visitors on IPv6 networks can reach you directly</li>
</ul>
<h2 id="cname-record-name-another-name">CNAME Record: Name → Another Name<a class="heading-anchor" href="#cname-record-name-another-name" aria-label="Link to this section">#</a></h2>
<p>CNAME is easiest to understand with a common setup: a blog on GitHub Pages.</p>
<p><strong>The default.</strong> GitHub hosts every Pages site at its own address:</p>
<ul>
<li>Personal site: <code>username.github.io</code></li>
<li>Project site: <code>username.github.io/repository-name</code></li>
</ul>
<p>Say my GitHub username is <code>vibhavari</code>. Then my site lives at <code>vibhavari.github.io</code>.</p>
<p><strong>The problem.</strong> I want my blog at <code>www.vibhavari.com</code> instead, because:</p>
<ul>
<li>A custom domain looks more professional</li>
<li>It&#39;s easier to remember</li>
<li>I control the branding</li>
<li>I can move away from GitHub Pages later without breaking links</li>
</ul>
<h4 id="how-cname-solves-this">How CNAME Solves This<a class="heading-anchor" href="#how-cname-solves-this" aria-label="Link to this section">#</a></h4>
<p>My content actually lives at <code>vibhavari.github.io</code>, on servers whose IP addresses GitHub controls, and can change. I don&#39;t want to copy those IPs into my DNS. I want to say &quot;<code>www.vibhavari.com</code> is whatever <code>vibhavari.github.io</code> is&quot;.</p>
<p>That&#39;s exactly a CNAME. In the DNS provider (Cloudflare, GoDaddy, Route53, etc.), I create:</p>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang"></span>
        <button type="button" class="code-copy">Copy</button>
      </div>
      <pre class="shiki"><code>www.vibhavari.com.  3600  IN  CNAME  vibhavari.github.io.</code></pre>
    </div><p>This means:</p>
<ul>
<li>&quot;When someone asks for <code>www.vibhavari.com</code>, look up <code>vibhavari.github.io</code> instead&quot;</li>
<li>The resolver follows the chain: <code>www.vibhavari.com</code> → <code>vibhavari.github.io</code> → (GitHub&#39;s A records) → IP address</li>
</ul>
<p>Then, in the repository settings, I tell GitHub to accept traffic for <code>www.vibhavari.com</code>, and GitHub adds a <code>CNAME</code> file containing <code>www.vibhavari.com</code> to the repository root.</p>
<p>So a CNAME record creates an alias: it maps one domain name to another (the canonical name). When a resolver meets a CNAME, it performs another lookup for the target. If GitHub changes its IPs tomorrow, my site keeps working.</p>
<aside class="callout callout-warning">
      <p class="callout-title">Warning</p>
      <div class="callout-body"><p>You CANNOT have a CNAME at the root domain (<code>example.com</code>) - only subdomains (<code>www.example.com</code>, <code>blog.example.com</code>, etc.). A CNAME can&#39;t share its name with any other record, and the root domain always needs NS records.</p>
</div>
    </aside>

<h2 id="ns-record-who-answers-for-this-domain">NS Record: Who Answers for This Domain<a class="heading-anchor" href="#ns-record-who-answers-for-this-domain" aria-label="Link to this section">#</a></h2>
<p>An NS record delegates a DNS zone to a specific <code>authoritative name server</code>. It tells resolvers which servers are allowed to answer questions about a domain. Every domain should have at least two NS records, for redundancy.</p>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang"></span>
        <button type="button" class="code-copy">Copy</button>
      </div>
      <pre class="shiki"><code>example.com. 86400 IN NS ns1.nameserver.com.</code></pre>
    </div><p>Think of a <strong>corporate directory</strong>: the main receptionist doesn&#39;t know everyone&#39;s extension. When you ask for Marketing, they say: &quot;Marketing is handled by extension 5000, let me transfer you.&quot; The NS record is that transfer.</p>
<h4 id="when-and-why-used-2">When and Why Used<a class="heading-anchor" href="#when-and-why-used-2" aria-label="Link to this section">#</a></h4>
<ul>
<li><strong>Primary use</strong>: Delegating DNS authority for a domain or subdomain</li>
<li><strong>When</strong>: Setting up a domain, delegating subdomains to different DNS providers, using a CDN</li>
<li><strong>Why</strong>: Lets different teams or services control their own part of a domain</li>
<li><strong>Example scenario</strong>: You register <code>example.com</code> at a registrar, then point its NS records to your DNS hosting provider (like Cloudflare or Route53)</li>
</ul>
<h2 id="mx-record-where-email-goes">MX Record: Where Email Goes<a class="heading-anchor" href="#mx-record-where-email-goes" aria-label="Link to this section">#</a></h2>
<p>An MX record names the mail servers that accept email for a domain. Each has a priority value (lower number = tried first), which allows fallback servers. When someone sends email to <code>user@example.com</code>, their mail server looks up the MX records to find where to deliver it.</p>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang"></span>
        <button type="button" class="code-copy">Copy</button>
      </div>
      <pre class="shiki"><code>example.com. 3600 IN MX 10 mail1.example.com.</code></pre>
    </div><ul>
<li>Priority: 10 (lower is preferred)</li>
<li>Mail server: <code>mail1.example.com</code></li>
</ul>
<p>Think of a <strong>company mail room with backups</strong>:</p>
<ul>
<li><strong>Priority 10</strong>: Main mail room - <code>mail1.example.com</code></li>
<li><strong>Priority 20</strong>: Backup mail room, if the main one is closed - <code>mail2.example.com</code></li>
<li><strong>Priority 30</strong>: Emergency off-site facility - <code>mail3.example.com</code></li>
</ul>
<p>The postal service tries the priority 10 location first. If it&#39;s unavailable, it tries priority 20, and so on.</p>
<h4 id="when-and-why-used-3">When and Why Used<a class="heading-anchor" href="#when-and-why-used-3" aria-label="Link to this section">#</a></h4>
<ul>
<li><strong>Primary use</strong>: Directing email to the correct mail servers</li>
<li><strong>When</strong>: Setting up email for your domain, for example with Google Workspace or Microsoft 365</li>
<li><strong>Why</strong>: Keeps email separate from web hosting, and gives you redundancy</li>
<li><strong>Example scenario</strong>: You use Google Workspace for email, so you create MX records:</li>
</ul>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang"></span>
        <button type="button" class="code-copy">Copy</button>
      </div>
      <pre class="shiki"><code>  example.com. IN MX 1 aspmx.l.google.com.
  example.com. IN MX 5 alt1.aspmx.l.google.com.
  example.com. IN MX 5 alt2.aspmx.l.google.com.</code></pre>
    </div><p>If the primary server is down, email automatically goes to the backups.</p>
<h2 id="txt-record-notes-for-machines">TXT Record: Notes for Machines<a class="heading-anchor" href="#txt-record-notes-for-machines" aria-label="Link to this section">#</a></h2>
<p>A TXT record stores arbitrary text on a domain. It was originally meant for human-readable notes, but today it&#39;s mostly used for machine-readable data: domain verification and email security policies (SPF, DKIM, DMARC). Each string can be up to 255 characters, and several strings can be combined.</p>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang"></span>
        <button type="button" class="code-copy">Copy</button>
      </div>
      <pre class="shiki"><code>example.com. 3600 IN TXT &quot;v=spf1 include:_spf.google.com ~all&quot;</code></pre>
    </div><p>Think of a notice board outside your house:</p>
<ul>
<li>&quot;This is indeed the Johnson residence&quot; (domain verification)</li>
<li>&quot;We only accept mail from USPS and FedEx&quot; (SPF)</li>
<li>&quot;Packages should be left with neighbor at #125&quot; (special instructions)</li>
</ul>
<h4 id="when-and-why-used-4">When and Why Used<a class="heading-anchor" href="#when-and-why-used-4" aria-label="Link to this section">#</a></h4>
<ul>
<li><strong>Primary use</strong>: Domain verification, email authentication, security policies</li>
<li><strong>When</strong>: Proving domain ownership, preventing email spoofing, setting up third-party services</li>
<li><strong>Why</strong>: A flexible way to attach data to a domain without inventing new record types</li>
</ul>
<p><strong>Common Use Cases:</strong></p>
<p><strong>1. Domain Verification</strong></p>
<ul>
<li><strong>When</strong>: Setting up Google Workspace, Microsoft 365, or any service that needs proof you own the domain</li>
<li><strong>Example</strong>: <code>example.com. IN TXT &quot;google-site-verification=abc123xyz&quot;</code></li>
<li><strong>Why</strong>: Proves you control the domain before the service activates</li>
</ul>
<p><strong>2. SPF (Sender Policy Framework)</strong></p>
<ul>
<li><strong>When</strong>: Configuring email to prevent spoofing</li>
<li><strong>Example</strong>: <code>example.com. IN TXT &quot;v=spf1 ip4:192.0.2.1 include:_spf.google.com ~all&quot;</code></li>
<li><strong>Why</strong>: Lists which servers may send email for your domain, which reduces spam and phishing</li>
<li><strong>Translation</strong>: &quot;Only these mail servers can send email claiming to be from @example.com&quot;</li>
</ul>
<h2 id="the-whole-domain-as-a-city">The Whole Domain as a City<a class="heading-anchor" href="#the-whole-domain-as-a-city" aria-label="Link to this section">#</a></h2>
<ul>
<li><strong>NS Records</strong> → City charter (who governs)</li>
<li><strong>A/AAAA Records</strong> → Building addresses (where things are)</li>
<li><strong>CNAME Records</strong> → Street signs &amp; aliases (how to find things)</li>
<li><strong>MX Records</strong> → Post office system (mail delivery)</li>
<li><strong>TXT Records</strong> → Business licenses &amp; permits (verification &amp; security)</li>
</ul>
<p>So back to <code>vibhavari.com</code>: a CNAME for the blog, MX records for email, a TXT record for Google, and NS records saying who answers for all of them. One domain, a different record for every job.</p>
