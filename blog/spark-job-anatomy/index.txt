21:T28a2,<p>Here&#39;s a small Spark program: two DataFrames, one repartitioned into 5 partitions and the other into 6, joined and summed. Open the Spark UI and one of its stages has <strong>200 tasks</strong>. Nothing in the code says 200.</p>
<p>Where that number comes from is the key to reading the Spark UI:</p>
<blockquote>
<p>One action creates a job. Every shuffle starts a new stage. Every partition becomes a task.</p>
</blockquote>
<p>This post walks through each of those three rules with the Spark UI open, and ends with where the 200 came from.</p>
<!-- truncate -->

<h2 id="every-action-creates-a-job">Every Action Creates a Job<a class="heading-anchor" href="#every-action-creates-a-job" aria-label="Link to this section">#</a></h2>
<p>Each application is made up of one or more Spark jobs, and a job is created for <Highlight color="#3e6980">each action</Highlight> (<code>count</code>, <code>collect</code>, <code>write</code>, …). Jobs triggered from the same thread run one after another. They only run in parallel if you submit them from separate threads.</p>
<p>Since Spark <a href="https://en.wikipedia.org/wiki/Lazy_evaluation">evaluates lazily</a>, transformations alone do nothing. If there are no actions, there are no jobs:</p>
<p><img src="/posts/2025-01-21-spark-job-anatomy/assets/no-actions-no-jobs.png" alt="no-action-no-job" loading="lazy" /></p>
<p>Call an action on the DataFrame, and a job appears:</p>
<p><img src="/posts/2025-01-21-spark-job-anatomy/assets/job-created.png" alt="action-job" loading="lazy" /></p>
<p>Each job breaks down into a series of stages, and the number of stages depends on how many shuffles the job needs.</p>
<h2 id="every-shuffle-starts-a-new-stage">Every Shuffle Starts a New Stage<a class="heading-anchor" href="#every-shuffle-starts-a-new-stage" aria-label="Link to this section">#</a></h2>
<p>A stage is a group of tasks that Spark can run together to perform the same operation across multiple machines. Spark tries to fit as much work as possible into one stage, but it has to start a new one whenever there&#39;s a shuffle.</p>
<p>A shuffle happens when <Highlight color="#3e6980">Spark redistributes data across partitions or nodes in the cluster</Highlight>. Sorting a DataFrame, or grouping by key (which sends all records with the same key to the same node), both need one. Data physically moves between executors, so everything before the shuffle has to finish before anything after it can start. That boundary is the stage boundary.</p>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang"></span>
        <button type="button" class="code-copy">Copy</button>
      </div>
      <pre class="shiki"><code>scala&gt; val df1 = spark.range(2, 10000000, 2)
val df1: org.apache.spark.sql.Dataset[Long] = [id: bigint]

scala&gt; val step1 = df1.repartition(5)
val step1: org.apache.spark.sql.Dataset[Long] = [id: bigint]

scala&gt; step1.count()
val res0: Long = 4999999</code></pre>
    </div><p><img src="/posts/2025-01-21-spark-job-anatomy/assets/shuffles.png" alt="stages" loading="lazy" /></p>
<p>One action (<code>count</code>), so one job, split into three stages:</p>
<ul>
<li><strong>Stage 0</strong> is the <code>range</code> that creates the DataFrame. On this machine, <code>range</code> produced <code>8 partitions</code> by default.</li>
<li><strong>Stage 1</strong> is the <code>repartition</code>. It shuffles the data into <code>5 partitions</code>.</li>
<li><strong>Stage 2</strong> is the <code>count</code> itself.</li>
</ul>
<p>Now the program from the start of this post:</p>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang">Scala</span>
        <button type="button" class="code-copy">Copy</button>
      </div>

<p>Stages 3 and 4 work on each DataFrame separately, and each ends at the join, which is another shuffle. The stage after the join is the one with 200 tasks.</p>
<h2 id="every-partition-becomes-a-task">Every Partition Becomes a Task<a class="heading-anchor" href="#every-partition-becomes-a-task" aria-label="Link to this section">#</a></h2>
<p>A task is a <Highlight color="#3e6980">unit of computation applied to a unit of data (the partition)</Highlight>. Each task runs a stage&#39;s transformations on one partition, on a single executor. So a stage has exactly as many tasks as its data has partitions.</p>
<p>That&#39;s where the 200 comes from. When a DataFrame shuffle happens, the number of output partitions isn&#39;t taken from your input; it&#39;s taken from <code>spark.sql.shuffle.partitions</code>, which <strong>defaults to 200</strong>. The join shuffled both sides into 200 partitions, so the next stage ran 200 tasks, whether the data needed them or not.</p>
<p>You can change it:</p>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang">Scala</span>
        <button type="button" class="code-copy">Copy</button>
      </div>
      <pre class="shiki github-light-high-contrast" tabindex="0"><code><span class="line"><span style="color:#0E1116">spark.conf.set(</span><span style="color:#032563">"spark.sql.shuffle.partitions"</span><span style="color:#0E1116">, </span><span style="color:#023B95">50</span><span style="color:#0E1116">)</span></span></code></pre>
    </div><aside class="callout callout-note">
      <p class="callout-title">Note</p>
      <div class="callout-body"><p>A good rule of thumb: the number of partitions should be larger than the number of executor cores on your cluster, often by a few times, so every core has work. On a small dataset, 200 tiny partitions is mostly overhead.</p>
</div>
    </aside>

<tr>
<td><strong>Tasks &amp; Executors</strong></td>
<td>- One Task runs on one Executor (it can’t move mid-task). <br/> - An Executor can run multiple Tasks (depending on its available cores).</td>
</tr>
<tr>
<td><strong>Partitions &amp; Tasks</strong></td>
<td>- Processing one partition = one Task. <br/> - The number of Tasks in a Stage often equals the number of partitions for that data.</td>
</tr>
<tr>
<td><strong>Partitions &amp; Executors</strong></td>
<td>- A partition stays on one Executor while it’s being processed. <br/> - Each Executor can hold 0 or more partitions in memory or on disk.</td>
</tr>
<tr>
<td><strong>Executors &amp; Nodes</strong></td>
<td>- 1 Executor corresponds to 1 JVM running on 1 physical/virtual Node. <br/> - Each Node can host 0 or more Executors.</td>
</tr>
</tbody></table>
<p>Or in one line: <strong>Application → Jobs → Stages → Tasks</strong>, where each task processes one partition on one executor.</p>
