21:T1d26,<p>If you have ever played a video game, you know the anxiety of facing a difficult boss. What is the first thing you do before walking through that boss door? You save your game.</p>
<p>Why? Because if you rush in and lose all your health, you don&#39;t want to restart the entire game from level one. You want to respawn right where you were, with all your items and progress intact.</p>
<blockquote>
<p><code>Git</code> is a save button for your code.</p>
</blockquote>
<p>It lets you create Save Points in your project. If you write a bunch of code and accidentally break your entire app, you don&#39;t have to panic. You &quot;reload&quot; your last save, and you are back in business.</p>
<p>In this post, we&#39;ll go through the Git basics as a game: what Git is, the terms you&#39;ll keep hearing, and the six commands that take you from a new project to your first save.</p>
<h2 id="what-git-is">What Git Is<a class="heading-anchor" href="#what-git-is" aria-label="Link to this section">#</a></h2>
<p>Git is a distributed version control system: every developer&#39;s machine holds a complete copy of the repository, history included. You commit your changes locally, test them, and sync with a remote repository (like GitHub) when you&#39;re ready.</p>
<h3 id="snapshots-not-lists-of-changes">Snapshots, Not Lists of Changes<a class="heading-anchor" href="#snapshots-not-lists-of-changes" aria-label="Link to this section">#</a></h3>
<p>The major difference between Git and most other version control systems is the way Git thinks about data. Most version control systems store information as a list of file-based changes (deltas). Git instead stores a snapshot of your whole project every time you commit; files that didn&#39;t change aren&#39;t copied again, Git just points to the version it already has.</p>
<p>That design is why Git gives you:</p>
<ol>
<li><strong>Distributed Development</strong>: Every developer has a full copy of the repository, including its history, so you can work offline and browse history instantly.</li>
<li><strong>Branching and Merging</strong>: Creating a branch for a feature or bug fix is cheap, and merging it back is straightforward.</li>
<li><strong>Pull Requests and Code Reviews</strong>: Platforms like GitHub and GitLab build collaboration on top of Git with pull requests and code reviews.</li>
<li><strong>Data Integrity</strong>: Every file and commit is checksummed with a SHA-1 hash, so any corruption is detected.</li>
<li><strong>Speed</strong>: Most operations run locally, so committing, branching and merging are fast.</li>
</ol>
<h3 id="core-terms-in-git">Core Terms in Git<a class="heading-anchor" href="#core-terms-in-git" aria-label="Link to this section">#</a></h3>
<ol>
<li><strong>Repository (Repo)</strong>: A directory that contains your project files and the entire history of changes made to them. You push it to a remote server like GitHub or GitLab.</li>
<li><strong>Branch</strong>: A separate line of development. You create branches to work on features or bug fixes without affecting the main codebase.</li>
<li><strong>Commit</strong>: A &quot;Save Point&quot;. Each commit has a unique ID and a message describing the changes.</li>
<li><strong>Stage</strong>: Choosing which changes go into your next commit.</li>
<li><strong>HEAD</strong>: The &quot;You are here&quot; marker: which Save Point (commit) you&#39;re currently playing.</li>
</ol>
<p>It&#39;s also important to understand <code>The Three States</code> a file can be in:</p>
<ol>
<li><strong>Modified</strong>: The file has changed, but the change isn&#39;t committed yet.</li>
<li><strong>Staged</strong>: The change is marked to go into the next commit. Only staged changes are included.</li>
<li><strong>Committed</strong>: The change is saved in the repository.</li>
</ol>
<p><img src="/posts/2026-01-13-git-essentials/assets/three-states.png" alt="The Three States in Git" loading="lazy" /></p>
<h2 id="your-first-save-point-step-by-step">Your First Save Point, Step by Step<a class="heading-anchor" href="#your-first-save-point-step-by-step" aria-label="Link to this section">#</a></h2>
<ol>
<li>Start a New Game with <code>git init</code>: This creates a new Git repository in your project directory.</li>
</ol>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang"></span>
        <button type="button" class="code-copy">Copy</button>
      </div>
      <pre class="shiki"><code>mkdir git-game
cd git-game
git init</code></pre>
    </div><ol start="2">
<li>Check your status with <code>git status</code>: This shows the current state of your repository, including changes that aren&#39;t committed yet. It&#39;s like checking your inventory and health.</li>
</ol>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang"></span>
        <button type="button" class="code-copy">Copy</button>
      </div>
      <pre class="shiki"><code>git status</code></pre>
    </div><ol start="3">
<li><p>Create Content - Create a file named story.txt and type &quot;Chapter 1: The Hero Wakes Up.&quot; If you run <code>git status</code> now, the file shows in red. Git sees a new file, but it isn&#39;t prepared to be saved yet.</p>
</li>
<li><p>Prepare the Save - <code>git add</code><br>In a game, you might organize your inventory before saving. In Git, this is called Staging. We tell Git which files go into the save.</p>
</li>
</ol>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang"></span>
        <button type="button" class="code-copy">Copy</button>
      </div>
      <pre class="shiki"><code>git add story.txt</code></pre>
    </div><aside class="callout callout-tip">
      <p class="callout-title">Tip</p>
      <div class="callout-body"><p>Type <code>git add .</code> to add EVERYTHING that changed at once.</p>
</div>
    </aside>

<p>Run <code>git status</code> again. The file turns green. It is now &quot;Staged&quot; and ready to be committed.</p>
<ol start="5">
<li>Create the Save Point - <code>git commit</code><br>This is the moment you actually press &quot;Save&quot;. Leave a message so you remember why you saved here.</li>
</ol>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang"></span>
        <button type="button" class="code-copy">Copy</button>
      </div>
      <pre class="shiki"><code>git commit -m &quot;Started the story with Chapter 1&quot;</code></pre>
    </div><p>Success! You have a permanent checkpoint. You can now delete story.txt, change it, or break it, and you can always return to this exact state.</p>
<ol start="6">
<li>View Your Saves - <code>git log</code><br>Want to see your list of save points?</li>
</ol>
<div class="code-block">
      <div class="code-head">
        <span class="code-lang"></span>
        <button type="button" class="code-copy">Copy</button>
      </div>
      <pre class="shiki"><code>git log</code></pre>
    </div><p>This prints a journal of every save: who made it, when, and the message they left.</p>
<hr>
<p><img src="/posts/2026-01-13-git-essentials/assets/overall.png" alt="Git Save Point" loading="lazy" /></p>
<p>Git lets you make mistakes, and in programming, making mistakes is how you learn. So save before the boss fight: commit before the risky refactor, then go ahead and break things.</p>
